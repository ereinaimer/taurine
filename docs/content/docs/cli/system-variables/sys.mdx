The `[sys.*]` namespace provides read-only access to core metadata about your machine and operating system. This is useful for creating snippets that adapt to different environments or for generating system reports.

## Reference Table

| Variable | Resolves To | Example Output |
| :--- | :--- | :--- |
| `[sys.os]` | Operating system name | `windows`, `linux`, `macos` |
| `[sys.osversion]` | Human-readable OS version | `Windows 11 (23H2)` |
| `[sys.arch]` | CPU architecture | `x86_64`, `aarch64` |
| `[sys.hostname]` | Machine name | `dev-workstation` |
| `[sys.user]` | Current OS username | `erein` |

## Usage

These variables are strictly read-only and return static strings based on your current system state at expansion time.

```text
OS:       [sys.os]
Version:  [sys.osversion]
User:     [sys.user]
```

## Practical Example: System Header

Use `[sys.*]` variables combined with [transformers](/docs/cli/dynamic-variables/transformers) to create a standardized header for your local logs or dev reports.

<Transformation
  template="REPORT | [sys.hostname | upper] | [sys.os | title] ([sys.arch]) | [date.iso]"
  input=">sys "
  result="REPORT | DEV-STATION | Windows (x86_64) | 2026-04-22"
/>

## Technical Details

- **Case Sensitivity**: Modifiers like `os` and `hostname` are case-insensitive.
- **Platform Specifics**: `[sys.user]` correctly resolves `USERNAME` on Windows and `USER` on Linux/macOS.
- **Transformers**: Standard transformers chain normally using unix pipes. For example, `[sys.user | upper]` will return the username in all caps.
- **Static Resolution**: Unlike the `[execute.*]` namespace, `sys` variables resolve instantly and do not trigger a spinner.
